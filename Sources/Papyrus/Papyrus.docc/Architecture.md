# Architecture

Papyrus가 대용량 PDF를 빠르게 열고, 안전하게 복구하고, 매끄럽게 그리기 위해 내부를
어떻게 구성하는지 설명합니다.

## 개요

Papyrus는 PDF를 다루는 두 가지 문제 — **파일 구조를 해석하는 것**과 **픽셀을
그리는 것** — 를 의도적으로 분리합니다.

파일 구조(교차 참조 테이블, 간접 객체, 페이지 트리, 메타데이터, 목차, 페이지별
텍스트)는 순수 Swift로 직접 파싱합니다. 이 계층에 외부 PDF 엔진을 두지 않는 이유는
대용량 문서에서 메모리 사용량과 지연 로딩 전략을 스스로 제어해야 하기 때문입니다.
수천 페이지 문서를 열 때 파일 전체를 메모리에 올리거나 모든 객체를 미리 해석하면
그 자체로 확장성의 한계가 됩니다. 직접 파싱하면 필요한 객체만, 필요한 시점에
읽어들이는 지연 로딩 구조를 설계 단계부터 보장할 수 있습니다.

반면 페이지를 실제 픽셀로 래스터화하는 작업은 플랫폼의 Core Graphics
(`CGPDFPage` → `CGContext`)에 위임합니다. 래스터화는 정확한 폰트 힌팅, 색 공간
변환, 안티앨리어싱처럼 운영체제가 이미 고도로 최적화해 둔 영역이라 직접 재구현할
이유가 없습니다. 대신 Papyrus가 직접 파싱해 얻은 페이지 지오메트리(크기, 회전,
좌표계)를 활용해 어떤 페이지의 어느 영역을 언제 그릴지 — 타일링, 캐싱, 프리페치
— 를 세밀하게 제어합니다.

즉 Papyrus는 "구조는 우리가, 픽셀은 시스템이" 원칙의 하이브리드 엔진입니다. 이
분리 덕분에 문서를 여는 속도와 메모리 사용량은 파싱 코어가 전적으로 책임지고,
렌더링 품질과 플랫폼 호환성은 Core Graphics가 보장합니다.

## 모듈 계층

Papyrus는 네 개의 모듈로 나뉘며, 각 모듈은 그 아래 계층에만 의존합니다.

```
Papyrus                 ← 엄브렐러: 위 세 모듈을 재노출
  └── PapyrusUI          ← SwiftUI 퍼사드 + 가상화 스크롤 뷰어
        └── PapyrusRendering  ← 타일 렌더링, 캐시, 워커 풀
              └── PapyrusCore    ← 파싱 코어 (구조·메타데이터·텍스트·검색)
```

- **`PapyrusCore`** 는 파일을 열고, 페이지 구조·메타데이터·목차·페이지별 텍스트를
  추출하고, 텍스트 검색을 제공합니다. Core Graphics나 SwiftUI에 의존하지 않는
  독립적인 계층으로, 서버 사이드 텍스트 추출처럼 화면이 필요 없는 용도로도 단독
  사용할 수 있습니다.
- **`PapyrusRendering`** 은 `PapyrusCore`가 해석한 페이지 지오메트리를 받아 실제
  픽셀(타일 이미지)을 생성하고 캐싱합니다. 뷰어 없이 특정 페이지의 썸네일이나
  프리뷰 이미지만 필요한 경우에도 이 계층만으로 충분합니다.
- **`PapyrusUI`** 는 `PapyrusRendering`이 만든 타일을 SwiftUI 뷰로 조립합니다.
  스크롤 가상화, 줌, 목차·검색 탐색을 담당하는 뷰어 컴포넌트를 제공합니다.
- **`Papyrus`** 는 위 세 모듈의 공개 API를 하나의 `import Papyrus`로 재노출하는
  엄브렐러 모듈입니다. 대부분의 앱은 이 모듈 하나만 가져오면 됩니다.

각 계층은 자신의 관심사만 노출합니다. 파싱 코어는 렌더링을 모르고, 렌더링은
SwiftUI를 모릅니다. 이 방향성 있는 의존 구조 덕분에 상위 계층 없이 하위 계층만
따로 테스트하거나 재사용할 수 있습니다.

## 대용량 문서 전략

Papyrus가 겨냥하는 시나리오는 수천 페이지 규모의 문서입니다. 이를 지탱하는 세
가지 전략이 있습니다.

**메모리 맵 파일 접근.** 문서를 열 때 파일 전체를 읽어 들이는 대신 메모리 맵으로
매핑합니다. 이후 모든 바이트 접근은 오프셋 기반 랜덤 액세스로 이루어지며, 운영체제의
페이지 캐시가 실제로 어떤 영역을 상주시킬지 결정합니다. 문서 크기와 무관하게
열기 자체의 메모리 오버헤드는 거의 일정합니다.

**지연 객체 로딩.** 간접 객체는 파일 안의 위치만 먼저 색인되고, 실제 내용(딕셔너리,
스트림 바이트)은 처음 참조되는 시점에만 파싱·디코딩됩니다. 스트림 디코딩 결과와
파싱된 객체는 바이트 예산 기반 캐시에 보관되어 반복 접근 비용을 낮추되, 문서 전체를
메모리에 쌓아두지는 않습니다.

**열기 비용은 교차 참조 구조에 비례합니다.** 문서를 여는 데 걸리는 시간은 페이지
수가 아니라 교차 참조(xref) 테이블의 크기와 형태에 좌우되도록 설계되어 있습니다.
페이지 트리는 처음 접근하는 시점에 한 번만 평탄화되어 페이지 인덱스 배열로
캐시되므로, 이후의 개별 페이지 접근·레이아웃 계산은 상수 시간에 가깝게
이루어집니다. 그 결과 수천 페이지 문서를 열어도 지연은 xref 파싱 시간에 수렴하고,
페이지 수 자체는 지배적인 변수가 되지 않습니다.

## 동시성 모델

문서 코어는 액터로 구현되어 매핑 파일, 교차 참조 테이블, 객체 캐시, 페이지 인덱스,
텍스트 캐시 같은 가변 상태를 전부 액터 격리 아래 소유합니다. 모든 객체 해석은
이 액터를 거치므로 동시에 여러 곳에서 같은 문서에 접근해도 데이터 경쟁이 발생하지
않습니다.

공개 타입인 `PapyrusDocument`는 `Sendable` 이며, 모든 프로퍼티·메서드는
`async`로 노출되고 반환값은 항상 값 타입(`Sendable`) 스냅숏입니다. 호출자는 액터의
내부 구조를 알 필요 없이 일반적인 `async`/`await` 코드로 문서를 다룹니다. 압축
해제나 콘텐츠 스트림 해석처럼 CPU를 많이 쓰는 작업은 액터가 필요한 데이터를 건넨
뒤 액터 밖에서 실행되어, 하나의 무거운 요청이 다른 모든 문서 접근을 막지 않습니다.

검색처럼 결과가 시간에 걸쳐 여러 건 생성되는 작업은 `AsyncThrowingStream`으로
노출됩니다. 호출자는 `for try await` 로 결과를 순서대로 소비하며, 필요하면 스트림을
조기에 취소해 나머지 페이지 스캔을 중단시킬 수 있습니다. 이 스트리밍 모델은 수천
페이지 문서를 검색할 때 전체 결과를 모을 때까지 기다리지 않고 첫 매치부터 즉시
화면에 반영할 수 있게 합니다.

래스터화 계층은 별도의 동시성 경계를 둡니다. Core Graphics의 PDF 문서 핸들은
스레드 안전하지 않으므로, 렌더링은 각자 독립된 핸들을 소유한 여러 워커 액터의
풀에서 병렬로 수행됩니다. 워커 밖으로는 완성된 이미지(변경 불가능하고 스레드 안전한
값)만 전달되며, Core Graphics 객체 자체는 액터 경계를 넘지 않습니다.

뷰어의 선택·메뉴·하이라이트 상태는 전부 메인 액터에서 관리되어 UI 갱신과 항상
동기화됩니다. 선택 히트테스트 인덱스를 구축하는 작업처럼 CPU를 많이 쓰는 계산은
순수 함수로 액터 밖에서 수행된 뒤 결과 값만 메인 액터에 반영되어, 무거운 계산이
화면 반응성을 막지 않습니다.

## 손상 내성

실제로 유통되는 PDF는 스펙을 정확히 지키지 않는 경우가 드물지 않습니다. Papyrus는
이를 예외적 상황이 아니라 기본 전제로 다룹니다: **경고하되 실패하지 않는다.**

문서를 여는 과정에서 흔한 구조적 결함 — 잘못된 오프셋, 손상된 교차 참조 행,
잘못 계산된 스트림 길이 등 — 을 만나면 가능한 범위에서 스스로 복구를 시도합니다.
교차 참조 테이블 자체가 신뢰할 수 없는 상태라면, 파일을 선형으로 스캔해 간접 객체
선언 패턴을 직접 찾아내는 복구 스캐너가 대체 경로로 동작합니다. 이런 복구가
개입했을 때는 문서를 여는 데 실패시키는 대신 `OpenWarning`으로 무엇이
비정상이었는지 기록해 호출자에게 남깁니다. 호출자는 경고 목록을 확인해 필요하면
사용자에게 "이 문서는 일부 복구되었습니다" 같은 안내를 보여줄 수 있습니다.

이 복구 지향 정책은 무작위·의도적으로 손상된 입력에 대한 지속적인 테스트로
뒷받침됩니다. 시드 문서에 결정론적 변이를 가한 입력 집합을 계속 실행해, 어떤
손상 패턴을 넣어도 크래시하거나 무한정 멈추지 않는다는 불변식을 검증합니다.
발견된 결함은 재현 가능한 형태로 회귀 코퍼스에 고정되어 이후에도 계속 검증됩니다.
파일이 정말로 PDF가 아니거나 복구가 불가능할 정도로 훼손된 경우에만
`PapyrusError`를 던져 명시적으로 실패합니다.

## 렌더링과 뷰어

페이지를 화면에 그리는 작업은 페이지 전체를 한 번에 래스터화하지 않고 **타일**
단위로 이루어집니다. 뷰포트에 보이는 영역과 그 주변만 실제 해상도로 그리고, 그
외 영역은 더 가벼운 페이지 단위 프리뷰로 대체합니다. 확대·축소 중에는 이미 그려진
레이어를 확대해 즉시 반응하다가, 제스처가 끝나는 시점에 새 배율로 다시 타일링합니다.

생성된 타일과 프리뷰는 각각 바이트 비용 기반 캐시에 보관되며, 캐시 예산은 기기의
물리 메모리에 비례해 정해집니다. 시스템이 메모리 압박 신호를 보내면 캐시는 즉시
예산을 줄이거나 필요시 전량 비워 다른 앱과 공존합니다. 렌더링 요청은 우선순위가
있어 — 현재 보이는 페이지의 공백을 없애는 요청이 항상 먼저 처리되고, 화면 밖
페이지의 사전 렌더링(프리페치)은 그 다음입니다. 사용자가 빠르게 스크롤해 어떤
페이지가 화면을 벗어나면, 아직 끝나지 않은 그 페이지의 렌더링 작업은 취소됩니다.

뷰어 자체는 **가상화된 스크롤**로 동작합니다. 수천 페이지 문서라도 실제로
메모리에 올라오는 페이지 뷰는 현재 보이는 범위와 그 인접 페이지 몇 개뿐이며,
나머지는 스크롤에 따라 재사용 풀에서 꺼내 쓰고 반납됩니다. 페이지 크기와 배치는
파싱 코어가 이미 읽어 둔 지오메트리로 문서를 열자마자 전부 계산되므로, 스크롤
위치로부터 어떤 페이지가 보여야 하는지 즉시 알 수 있습니다. 검색 결과 하이라이트나
현재 매치로의 이동도 같은 레이아웃 정보 위에서 이루어져, 렌더링 파이프라인과
독립적으로 동작합니다.

텍스트 선택은 플랫폼 제스처에서 시작합니다. 제스처가 공유 콘텐츠 좌표로 변환되고,
텍스트 지오메트리 히트테스트를 거쳐 줄 단위로 병합된 선택 quad가 오버레이로
그려진 뒤, 네이티브 편집 메뉴가 표시됩니다. 선택과 검색이 실제로 소비하는
텍스트는 `PageTextProvider`로 추상화되어 있어, 문서에 내장된 텍스트 추출 대신
OCR 같은 외부 결과를 그대로 꽂아 넣을 수 있습니다 — 좌표 계약은
<doc:ConnectingOCR>에서 다룹니다.

페이지 콘텐츠 위에 쌓이는 오버레이는 항상 같은 순서를 따릅니다: 지속
하이라이트가 가장 아래, 그 위에 검색 하이라이트, 가장 위에 선택 강조(iOS에서는
선택 핸들 포함)입니다. 검색은 사용자가 결과를 찾아가는 과업 지향적 상태라 항상
보이는 편이 자연스럽고, 선택은 사용자가 지금 직접 조작하는 대상이라 다른 모든
오버레이보다 위에서 즉각적인 피드백을 줍니다.
